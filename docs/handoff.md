## 1. 目的と経緯

### 目的
- TypeSafe AI の **Jev**（System One モデル）を少額のクレジット（$5）で試し、ユースケース別の小アプリを量産して、何に使えるかを見極める。
- 閉域・ローカル利用も検証する。Jev 本体は SaaS のみなので、SDK 互換の OSS **Kev**（ローカルで CPU 実行）へ `base_url` を差し替える構成を試す。
  - 動作確認に使ったマシンは GPU なし・RAM 30GB・16 コアで、Kev（0.8B 相当）を CPU で動かしている。

### 経緯（2026-09-25〜26）
1. **評価ハーネスと 8 つの小アプリ**
   - アプリ: メール仕分け・問い合わせ仕分け・障害報告トリアージ・投稿モデレーション・コミット種別の分類・契約条項のリスク判定・SNS 投稿のスロップ検知・書き換えの意味保持チェック
   - 評価ダッシュボードで、Jev・Kev・MOCK を切り替えて評価データと照合し、比較できるようにした。
   - ヘッダーに次を置いた。
     - 接続先の切替 `[Jev|Kev|MOCK]`（位置は固定）
     - 比較モード
     - Jev の利用額（目安、`var/usage.jsonl` に記録し再起動しても保持）
     - 利用上限（$1）
2. **企業向けの応用として「運用ダッシュボード」を構築**
   - 流れ: 問い合わせの自動仕分け ＋ 人の確認（しきい値ループ） ＋ Kev による前段のガードレール
   - 受信 → 個人情報ガードレール（Kev）→ 分類・抽出・優先度（Jev）→ 自動振り分け／分類の確認／エスカレーション → チャンネル（疑似 Slack）
   - 企画の A 案（自動仕分け）と B 案（Kev 前段）を採用し、次の 2 つも組み込んだ。
     - ② 候補から選ばせる抽出
     - ④ 多観点のスコアと重み付けの並べ替え
3. **追加機能とレビュー対応**
   - 個人情報の確認のまとめて処理
   - 担当者の管理と担当の自動推定・割り当て
   - 分類の確認の絞り込み
   - ツール「言い方チェック」（判定は Jev/Kev、書き換え案は Claude）
   - バックエンド・フロントエンドそれぞれのレビュー（サブエージェント）の指摘を反映した。
4. **利用者による伴走の動作確認**（進行中）
   - 動作確認の途中の要望で、次の 2 点を直した。
     - 個人情報の確認の編集を下書きとしてサーバに保持
     - ボタン名から「方針どおり」を廃止
   - `scripts/dev.sh` で Vite が止まる不具合を直した。
5. **実際の Slack とのつなぎ込みと、運用の仕上げ**
   - 実際の Slack とのつなぎ込み（Socket Mode）: 投稿の転送、エスカレーションの親の投稿とスレッドでの呼び出し、対応目安前の知らせ、受信用チャンネルからの取り込み（[ADR-0013](adr/0013-slack-socket-mode.md)、手順は [slack-setup.md](slack-setup.md)）。
   - エスカレーションの対応目安を営業時間で数えるようにした（`ops/sla.py`）。
   - ガードの切り替え: 「有効にする」（オフで元の本文のまま Jev に送る。デモ用）と「モデルで判定する」（オフで規則だけ。Kev を使わない）。
   - ブロックした件に、Kev による参考の分類と担当の推定を添える（自動では使わない）。
   - 検知漏れの報告（件の詳細から）と、その集計（閾値の調整の画面）。
   - 自動の閾値を超えても、判断が割れている件（分類の上位 2 つが僅差・不満度が両端に割れている）は分類の確認に回す。
   - 確信度を Jev の公式の定義で計算する（MOCK も同じ式。`core/confidence.py`）。
   - Kev に接続できないときは、ヘッダーに理由を出す（`core/kev_health.py`）。
   - 評価ダッシュボードの URL を `/eval/...` に移した（以前の `/apps/...` は移し替える）。最初の画面は運用ダッシュボード。
   - 表示名「氏名の可能性」を「未確定の候補」に変え、入力チェックのエラー（422）を日本語の短い文で出すようにした。
   - ボタン名を「マスクして仕分け」「そのまま仕分け」に変えた。
   - リポジトリを GitHub（`k-shimura7617/jevlab`）で管理するようにした。
6. **振り分けた件の完了と、Slack のリンク・完了スタンプ**（[ADR-0014](adr/0014-close-routed-items-in-jevlab.md)）
   - Slack のすべての投稿に、件の詳細（`/ops/items/{番号}`）へのリンクを付けた。
   - 振り分けた件も、件の詳細で「対応完了にする」ができる。最終の分類は、触らなければ「合っていた」、切り替えれば「修正した」として記録し、閾値の調整の正解に数える。
   - 完了すると、Slack の元の投稿のスレッドに返信し、✅ のリアクションを付ける（Bot Token Scopes に `reactions:write` が必要）。
7. **画面の手直しと、個人情報の混同行列**
   - 個人情報の確認の「確認対象」を、種類の一覧だけにした。閾値のスライダーを 0.05 刻みにした（抜き取る割合は 0.01 刻み）。
   - 閾値の調整に「個人情報の判定（Kev）」の混同行列を足した（候補ごと・候補外の残り。人が確認した件だけ）。
   - 利用者の要望: 画面の説明も応答も短く。例・補足の説明は付けない。
   - 受付箱で完了した件を既定で隠す（「完了を表示」で切り替え）。
   - 担当者の「担当」オン／オフ。オフの人は一覧に残したまま、推定の選択肢・割り当て・振り分け担当（当番）から外す。
   - 言い方チェック: 相手・場面を既定で「指定なし」に。履歴を開いても入力欄が動かない。結果の枠はスクロールなしで見える高さ。
8. **設定の自動保存**: 設定・担当者・Slack の欄は「保存」ボタンをやめ、文字の欄とスライダーはカーソルが外れたとき、チェック・選択は変えたときに保存する。保存できない値のまま離れるときだけ破棄してよいかを聞く。確認はガードレールを外す・「検出のみ」にする・担当者の削除だけ。
10. **受信シミュレータの高速**: 間隔「高速」で 0.1 秒ずつ受信し、同時に処理する件を 3 → 16 に上げる（Jev の同時の問い合わせも 16 まで）。Kev は 1 件ずつのまま。
11. **担当の仮の割り当てと ✅**: 確率が閾値に届かなくても、担当中の人のうち一番確率の高い人に仮で割り当ててメンションする（1 人ならその人。[ADR-0025](adr/0025-provisional-assignment.md)）。完了したら、その件で Slack に出した投稿すべてに ✅ を付ける（投稿していなければ付けない）。一括の割り当てのボタンは「全選択・全解除」「更新（追加 N・解除 N）」に。
12. **Kev の処理待ち**: ダッシュボードの「ガードレール」と個人情報の確認の画面に「Kev 待ち N 件・約 M 分（目安）」を出す。Kev が止まっていれば「止まっています」。見込みは最近 20 回の Kev の所要時間の中央値 × 件数。
13. **監査ログの CSV**: 運用 → 管理 → 監査ログ。期間・件・種類・文字コード（UTF-8／Shift_JIS）で絞って書き出す。本文・差出人・メモの本文・個人情報は出さない。書き出した記録を残す（[ADR-0026](adr/0026-audit-log-csv-without-content.md)）。主体は「人」まで（ログインがないため）。
9. **現場に合わせた取り込み**（[ADR-0015](adr/0015-import-existing-inquiries.md)）
   - ファイル取り込み: CSV（UTF-8・Shift_JIS）、.xlsx、.eml・mbox、Slack のエクスポート（.zip）。過去の分類・受信日時の列も取り込む。
   - 過去の問い合わせとして取り込む（試算用）: 仕分けまで行い、投稿・人の対応には回さず完了にする。閾値の調整で「想定ラベル・過去の分類」を選ぶと試算できる。
   - 件の詳細に「メールで返信」（`mailto:`）。
   - Slack・疑似チャンネルの投稿を、見出し・分類・理由・項目の 1 行ずつに。理由から「〜のため人が対応」を外した。
   - 利用者の環境: メールは主に Outlook。Excel・CSV もある。Shift_JIS は必須。
   - エスカレーションの完了は、エスカレーションのスレッドだけで知らせる（分類のチャンネルには投稿しない。[ADR-0024](adr/0024-escalation-close-notice-in-thread-only.md)）。
9. **言い方チェックの手直しと、作業の進め方の切り替え**
   - 相手に「部下」「指定なし」、場面に「指定なし」を足した。
   - 書き換えのモデルは sonnet（既定）と opus だけにした（haiku は遅く出力も長いため外した）。
   - 作業はコピーのステージングから、git の worktree と PR に移った（[ADR-0023](adr/0023-worktree-and-pr-workflow.md)）。
   - 決めたことを ADR-0016〜0024 に記録した。

## 2. 作業の約束ごと（このリポジトリで守ること）

### やりとり
- 日本語で、簡潔に応答する（コード・識別子は英語）。
- 変更した差分やコード全文を応答に貼らない。挙動・検証結果・確認手順を書く（コードは利用者がエディタでレビューする）。
- **実装の区切りや最終応答では、毎回その応答だけで分かる完結したレポートを出す。**
  - 中身: 何を作った／直したか（レビュー指摘は「指摘 → 対応」の対で）、使い方、検証結果（テスト件数・Playwright で確かめたこと）、残っていること。
  - 予約起動や再開のときに「何もしていません」だけを返さない。
- 複雑なタスクは、実装前に計画を示して承認を得る。
- アプリを修正したら、その区切りで `docs/` の資料（Markdown と HTML）も更新する。区切りが判断しにくいときは「資料を更新しますか」と提案して許可を得る。

### 課金とサーバ
- **実際の Jev の実行（課金あり）は利用者が行う。** こちらの検証は MOCK か Kev で行う。
- **Kev のインストール・起動は利用者が行う**（既定 http://127.0.0.1:8009）。
- **利用者が動作確認に使っているサーバ（8000 番と Vite の 5173 番、`scripts/dev.sh`）を止めたり、状態を変えたりしない。**
  - 読み取りの確認は構わない。
  - 検証は別ポート（例: 8010）のテスト用サーバで行う。
- **修正は git の worktree で行う**（[ADR-0023](adr/0023-worktree-and-pr-workflow.md)。以前のコピーによるステージングは廃止）。
  - `dev.sh` は `src/` の変更で自動的に再起動し、Vite は画面を差し替える。利用者の作業ツリーを直接編集すると、動作確認を壊すおそれがある。
  - 着手前に `git fetch` し、main を `--ff-only` で最新にする。
  - worktree のブランチで実装とテストを済ませる。利用者の作業ツリーへの反映は、利用者の GO を得てから行う。
  - コミット・push・PR の作成は、利用者に確認してから行う。
  - 利用者は Claude Code の Web セッションでも PR を作っている。同時に触っているファイルは避ける（利用者が教える）。
  - 反映で再起動・再読み込み・依存の追加（`uv sync`）が必要になるときは、事前に 1 行で伝える。

### 秘密と安全
- **`.env` と `.env.example` は読まない・表示しない・変更しない。** API キーは利用者が `.env` に入れる。
- API キーはサーバ側だけで使う。サーバは 127.0.0.1 だけで待ち受ける。データはダミーだけを使う。

### Git・ドキュメント・テスト
- 確認なしにコミット・push しない（リポジトリは GitHub の `k-shimura7617/jevlab`）。
- README やドキュメントを頼まれずに作成・変更しない。ただし `docs/` 一式は利用者の依頼で作成したもので、上の方針で更新する。
- テストを確認なしに削除・コメントアウトしない。既存の動作するコードを理由なくリファクタリングしない。

### コードの書き方と検証
- 関数型寄りで、副作用を小さくする。
- 型を厳密にする（TypeScript で `any` を使わず `unknown` にする）。エラーは握りつぶさず、意味のあるメッセージを付ける。
- 複数行のコメントは、文字数ではなく意味の切れ目で改行する。
- 画面の挙動は Playwright（playwright MCP）で確かめる。スクリーンショットは `.playwright-mcp/` に置く。

## 3. 構成の概要

```
ブラウザ（React SPA）
  │  /api/*（同一オリジン）
  ▼
FastAPI（src/jevlab/web.py、127.0.0.1:8000）
  ├─ 評価ハーネス（/api/apps, /api/runs）── core/engine.py ── core/client.py ─┬─ Jev（api.typesafe.ai、課金）
  ├─ 運用（/api/ops）── ops/pipeline.py（ワーカー・シミュレータ）─────────────├─ Kev（127.0.0.1:8009、ローカル）
  │                      └─ ops/store.py（SQLite: var/ops.db）                  └─ MOCK（API を呼ばない）
  ├─ ツール（/api/tools）── tools/tone.py ── core/generator.py ── claude -p（Claude Code、サブスク枠）
  └─ Slack のコネクタ ── ops/slack.py ── Slack（Socket Mode。伏せた見出しの転送と、受信用チャンネルの取り込み）
```

- **接続先（target）:** `jev` / `custom`（Kev などの互換サーバ）/ `mock` の 3 種類。1 つのサーバで同時に使い分ける。
  - Jev は `TYPESAFE_API_KEY` があるときだけ使える。
  - 既定の接続先は `JEVLAB_DEFAULT_TARGET` で決まる。
- **画面:** Vite 8 + React 19 + TypeScript（strict）+ react-router 8。
  - `frontend/` をビルドすると `src/jevlab/static/` に出力され、FastAPI が配信する。
  - 開発時は Vite（5173）が `/api` を FastAPI に中継する。
- **Python:** 3.12、uv で管理。依存は fastapi・slack-sdk・typesafe-sdk・uvicorn だけ（開発用に pytest と ruff）。

### ファイルの地図

| パス | 役割 |
|---|---|
| `src/jevlab/web.py` | FastAPI 本体。起動時（lifespan）に接続先・Store・Pipeline・ワーカー・シミュレータ・書き換えの同時実行枠を用意し、評価 API と SPA の配信を持つ |
| `src/jevlab/core/target.py` | 接続先の決定（環境変数だけから決まる） |
| `src/jevlab/core/client.py` | TypeSafe SDK クライアントの生成。MOCK の応答を作る。Kev の待ち時間は `KEV_TIMEOUT_S`（既定 120 秒） |
| `src/jevlab/core/confidence.py` | Jev の確信度の定義（Choice・Score の確率から計算） |
| `src/jevlab/core/kev_health.py` | Kev に接続できるかの確認（結果を 5 秒使い回す） |
| `src/jevlab/core/engine.py` | アプリ定義（AppSpec）、判定結果の表示用変換（`answer_views`）、評価データとの照合と集計 |
| `src/jevlab/core/metrics.py` | 正解率・Brier・MAE・信頼度曲線・ECE |
| `src/jevlab/core/budget.py` | Jev の料金計算（入力 $0.042/100 万トークン、出力無料）と利用上限（既定 $1、`JEVLAB_BUDGET_USD`）。`var/usage.jsonl` に記録 |
| `src/jevlab/core/runs.py` | 評価履歴（`var/runs.jsonl`） |
| `src/jevlab/core/generator.py` | 文章生成の抽象（Generator）と `claude -p` 実装。API キーを子プロセスに渡さない |
| `src/jevlab/apps/<name>/` | 評価用の小アプリ（`spec.py`・`questions.py`・`dataset.jsonl`）×8 |
| `src/jevlab/ops/models.py` | 運用のデータ型（Item・Settings・StaffMember など）と既定値 |
| `src/jevlab/ops/store.py` | SQLite の保存（items / events / posts / pii_misses / seen_messages / settings）。番号は連番で、空にしても再利用しない |
| `src/jevlab/ops/pii.py` | 個人情報の候補を規則（正規表現）で検出。マスク・ブロックの適用 |
| `src/jevlab/ops/questions.py` | 運用で Jev/Kev に投げる質問（ガード・分類・項目抽出・優先度・担当の推定） |
| `src/jevlab/ops/pipeline.py` | 処理の本体（受信 → ガード → 分類 → 振り分け）、人の操作（確定・割り当て・完了など）、ワーカー |
| `src/jevlab/ops/simulator.py` | デモの受信シミュレータ（`demo_inbox.jsonl` の 64 件を順に流す） |
| `src/jevlab/ops/tuning.py` | しきい値ごとの自動処理率と誤り率の曲線、しきい値の提案 |
| `src/jevlab/ops/misses.py` | 検知漏れの報告の集計と、「候補外に残っている可能性」の閾値の目安 |
| `src/jevlab/ops/importers.py` | 既存の問い合わせのファイルを読む（CSV・.xlsx・.eml・mbox・Slack のエクスポート） |
| `src/jevlab/ops/pii_eval.py` | 個人情報の判定（Kev）の混同行列（人が確認した件だけ） |
| `src/jevlab/ops/sla.py` | エスカレーションの対応目安（営業時間で数える） |
| `src/jevlab/ops/slack.py` | 実際の Slack とのつなぎ込み（Socket Mode。送信・スレッド・知らせ・受信） |
| `src/jevlab/ops/api.py` | 運用の API（`/api/ops/...`） |
| `src/jevlab/tools/tone.py` | 言い方チェックの質問・判定ロジック・書き換えのプロンプト |
| `src/jevlab/tools/reply.py` | 返信前チェック（答えているか・方針を超えた約束・謝罪・足りない情報・言い方。直した案は Claude） |
| `src/jevlab/tools/contract.py` | 契約・規約チェック（条項に分け、評価アプリ contract の質問を条項ごとに判定。説明は Claude） |
| `src/jevlab/tools/api.py` | ツールの API（`/api/tools/...`） |

## 4. 主な設計判断と理由

詳細は `docs/adr/` にまとめる。要点は次のとおり。

| 判断 | 理由 |
|---|---|
| 1 つのサーバで Jev・Kev・MOCK を並べて使う（ヘッダーで切替・比較） | 同じデータで差を数字として見るため。閉域で Kev へ差し替える判断材料にする |
| 個人情報のガードは「規則で候補を拾う＋氏名だけモデルに聞く」 | 形で決まる種類（電話・メール・カード等）は規則のほうが確実で速い。形で決まらない氏名だけ Kev に「個人情報か」を聞く（Noul）。候補外に残っている可能性も 1 問で聞く |
| ガードの接続先は Kev か MOCK のみ（Jev は不可） | マスク前の本文を外部に出さないため |
| 個人情報の扱いはマスク／ブロック／検出のみの 3 択 | Amazon Bedrock Guardrails と同じ考え方。ブロックした件は人に回すか、Kev だけで仕分ける |
| 分類・項目抽出・優先度・担当の推定を 1 回の問い合わせにまとめる | Jev は 1 リクエスト内の質問を並列に判定し、質問を足しても増えるのは入力トークンだけだから |
| 項目抽出は「候補を選ばせる」方式 | Jev は文章を生成しない。規則で拾った候補を Choice のキーにし、「該当なし」を加えて選ばせる |
| 振り分けは確信度のしきい値で決める（既定: 自動 ≥0.9、確認待ち ≥0.5、それ未満はエスカレーション） | 強い不満・緊急は業務ルールで常にエスカレーション。しきい値は「閾値の調整」画面で目標の誤り率から逆算して提案する |
| 学習ループはモデルの再学習ではなく「しきい値の調整」と「例を読ませる」 | Jev には fine-tuning がない。人の確認結果を正解にしきい値を見直し、担当の推定では最近の完了例を判定のたびに渡す |
| 担当は、推定した担当の確率が高いとき（既定 ≥0.7）だけ自動で割り当てる | 残りは推定を表示して人が決める。確信度は選択肢の数（人数）で意味が変わるので確率で判定する。推定の当たり具合は、人が決めた件だけで測る（自動のままの件は必ず一致するため） |
| 確信度は Jev の公式の定義で扱い、判断が割れた件は人に回す | 分類の上位 2 つが僅差、不満度が両端に割れた件は、確信度が高くても分類の確認へ。強い不満は「2」の確率で判定（[ADR-0017](adr/0017-confidence-semantics.md)） |
| ガードは「規則だけ」にも切り替えられる | Kev が遅い・止まっているときも処理を進める。候補はすべてマスクする（[ADR-0016](adr/0016-guard-rules-only-mode.md)） |
| 外に出る見出し（投稿・担当の例）は、個人情報の候補をすべて伏せる | 伏せすぎは読みにくいだけだが、漏れは取り返せない |
| まとめて処理では、編集していない件の候補をすべてマスクする。人が編集した件は、その下書きで処理する | 本文を見ていない件は安全側に倒し、人の判断があればそれを尊重する |
| 言い方チェックは「判定＝Jev/Kev、生成＝Claude」 | Jev は判定だけを返す。書き換えは判定結果を入力に Claude が作り、それを Jev で判定し直して比べる |
| 書き換えは `claude -p`（サブスク枠）で、Generator の抽象の裏に置く | すぐに試せ、あとで Anthropic API 版に差し替えられる。既定は sonnet（6 文面 × 3 モデルの比較で速さと質の釣り合いが最良） |
| 運用データは SQLite 1 ファイル（`var/ops.db`） | デモ・検証用途で十分。読み出し・変更・保存をロックの中で行い、ワーカーと画面操作の競合を防ぐ |
| 実際の Slack は Socket Mode ＋ 同期 SDK で、投稿の転送としてつなぐ | 127.0.0.1 のままで双方向につながり、仕分けの処理は Slack を知らずに済む（[ADR-0013](adr/0013-slack-socket-mode.md)） |
| 検知漏れは記録だけ残し、閾値の見直しに使う | 送った本文は取り消せない。個人情報そのものは保存せず、種類・位置・報告時の確率だけ残す。報告した範囲は以後の見出しで伏せる（[ADR-0020](adr/0020-measure-guard-with-reviews-and-miss-reports.md)） |
| SNS のアカウント名とプロフィールの URL は個人情報として規則で拾う | 個人を特定しうる。一般の URL は対象外（[ADR-0021](adr/0021-sns-accounts-as-pii.md)） |

## 5. 起動・テスト・検証

  - `SLACK_BOT_TOKEN`・`SLACK_APP_TOKEN`（実際の Slack とつなぐときだけ）

### テスト用サーバ（Claude が検証に使う）
- 利用者のサーバとぶつからないよう、別ポートと別のデータ置き場で起動する。

## 8. 既知の落とし穴（このプロジェクトで実際に踏んだもの）

| 落とし穴 | 対処 |
|---|---|
| `pkill -f uvicorn...` を、同じ文字列を含むシェルコマンドの中で実行すると、そのシェル自身が止まる（終了コード 144） | `pkill -f "[u]vicorn ..."` のように角括弧で自分自身に一致しない形にし、起動スクリプトとは別のコマンドで実行する |
| `scripts/dev.sh` で Vite（5173）が起動直後に止まり（状態 `T`）、画面が開かない | `set -m` で別のプロセスグループにした裏の Vite が端末の入力を読み、SIGTTIN で停止していた。Vite の入力を `/dev/null` にして解決。停止時は `kill -CONT` で再開させてから終了させる |
| pydantic のモデルに `target` という名前の項目を作ると、同名のモジュール `target` を型注釈で参照できなくなる（`'str' object has no attribute 'Target'`） | `from jevlab.core.target import Target` のように型を直接 import する |
| Kev で質問数が多い判定（言い方チェックの 17 問）が 10 秒でタイムアウトした | Kev クライアントの待ち時間を 120 秒に延ばした（`KEV_TIMEOUT_S`） |
| `asyncio.Semaphore` をモジュールの読み込み時に作ると、最初に使ったイベントループに結び付き、別のループ（別の TestClient）で落ちる | 起動時（lifespan）に `app.state` に作る |
| `claude -p` に親プロセスの環境変数が渡り、`ANTHROPIC_API_KEY` があると従量課金で動く | 子プロセスには `TYPESAFE_*`・`KEV_*`・`ANTHROPIC_API_KEY` を渡さない。API 課金に切り替えるときだけ `JEVLAB_CLAUDE_USE_API_KEY=1` にする |
| Score（段階評価）の値は段階の期待値。「くだけすぎ」と「堅すぎ」に割れると真ん中（適切）に見える | 真ん中が良い軸は「適切」の段階の確率で判定する |
| MOCK の確信度が一定だと、何も自動で振り分けられない | MOCK は文面から決まる疑似乱数で確信度を散らしている |
| ダークモード用の CSS の一括指定で、Slack 風のサイドバーの文字が暗くなった | 除外クラス（`.ch-btn` など）を足す |
| 文面の JSON を Playwright の中で扱うとき、`URL`・`Buffer` がない | 正規表現やファイルのパスで代用する |
| 待機に `sleep` を前面で使うとブロックされる環境がある | バックグラウンド実行や、条件を満たすまで待つループを使う |
| CJK（日本語）の判定精度は英語より低い（TypeSafe の注意事項） | 質問文は短く、1 問 1 条件にし、候補を選ばせる形にする |
| クラウドのセッションから GitHub に push すると 403 になることがある | GitHub の接続し直しと、Claude GitHub App のインストールを利用者に頼む。直ったら push し直す |
| クラウドのセッションは利用者の PC とは別の環境で、利用者のサーバ（8000・5173・8009）には届かない | 画面や Slack の設定は利用者の手元で行ってもらい、手順を案内する |
