## 1. 目的と経緯

### 目的
- TypeSafe AI の **Jev**（System One モデル）を少額のクレジット（$5）で試し、ユースケース別の小アプリを量産して、何に使えるかを見極める。
- 閉域・ローカル利用も検証する。Jev 本体は SaaS のみなので、SDK 互換の OSS **Kev**（ローカルで CPU 実行）へ `base_url` を差し替える構成を試す。
  - 動作確認に使ったマシンは GPU なし・RAM 30GB・16 コアで、Kev（0.8B 相当）を CPU で動かしている。

### 経緯（2026-09-25〜26）
1. **評価ハーネスと 8 つの小アプリ**
   - アプリ: メール仕分け・問い合わせ仕分け・障害報告トリアージ・投稿モデレーション・コミット種別の分類・契約条項のリスク判定・SNS 投稿のスロップ検知・書き換えの意味保持チェック
   - 評価ダッシュボードで、Jev・Kev・MOCK を切り替えて評価データと照合し、比較できるようにした。
   - ヘッダーに次を置いた。
     - 接続先の切替 `[Jev|Kev|MOCK]`（位置は固定）
     - 比較モード
     - Jev の利用額（目安、`var/usage.jsonl` に記録し再起動しても保持）
     - 利用上限（$1）
2. **企業向けの応用として「運用ダッシュボード」を構築**
   - 流れ: 問い合わせの自動仕分け ＋ 人の確認（しきい値ループ） ＋ Kev による前段のガードレール
   - 受信 → 個人情報ガードレール（Kev）→ 分類・抽出・優先度（Jev）→ 自動振り分け／分類の確認／エスカレーション → チャンネル（疑似 Slack）
   - 企画の A 案（自動仕分け）と B 案（Kev 前段）を採用し、次の 2 つも組み込んだ。
     - ② 候補から選ばせる抽出
     - ④ 多観点のスコアと重み付けの並べ替え
3. **追加機能とレビュー対応**
   - 個人情報の確認のまとめて処理
   - 担当者の管理と担当の自動推定・割り当て
   - 分類の確認の絞り込み
   - ツール「言い方チェック」（判定は Jev/Kev、書き換え案は Claude）
   - バックエンド・フロントエンドそれぞれのレビュー（サブエージェント）の指摘を反映した。
4. **利用者による伴走の動作確認**（進行中）
   - 動作確認の途中の要望で、次の 2 点を直した。
     - 個人情報の確認の編集を下書きとしてサーバに保持
     - ボタン名から「方針どおり」を廃止
   - `scripts/dev.sh` で Vite が止まる不具合を直した。

## 2. 作業の約束ごと（このリポジトリで守ること）

### やりとり
- 日本語で、簡潔に応答する（コード・識別子は英語）。
- 変更した差分やコード全文を応答に貼らない。挙動・検証結果・確認手順を書く（コードは利用者がエディタでレビューする）。
- **実装の区切りや最終応答では、毎回その応答だけで分かる完結したレポートを出す。**
  - 中身: 何を作った／直したか（レビュー指摘は「指摘 → 対応」の対で）、使い方、検証結果（テスト件数・Playwright で確かめたこと）、残っていること。
  - 予約起動や再開のときに「何もしていません」だけを返さない。
- 複雑なタスクは、実装前に計画を示して承認を得る。
- アプリを修正したら、その区切りで `docs/` の資料（Markdown と HTML）も更新する。区切りが判断しにくいときは「資料を更新しますか」と提案して許可を得る。

### 課金とサーバ
- **実際の Jev の実行（課金あり）は利用者が行う。** こちらの検証は MOCK か Kev で行う。
- **Kev のインストール・起動は利用者が行う**（既定 http://127.0.0.1:8009）。
- **利用者が動作確認に使っているサーバ（8000 番と Vite の 5173 番、`scripts/dev.sh`）を止めたり、状態を変えたりしない。**
  - 読み取りの確認は構わない。
  - 検証は別ポート（例: 8010）のテスト用サーバで行う。
- **修正はステージング用のコピーで行う**（ステージング運用）。
  - `dev.sh` は `src/` の変更で自動的に再起動し、Vite は画面を差し替える。そのため作業中のリポジトリを直接編集すると、利用者の動作確認を壊すおそれがある。
  - リポジトリのコピー（`.env`・`var/`・`.venv/` を除く）で実装とテストを済ませる。
  - 反映は区切りごとに、利用者の GO を得てから行う。
  - 反映で再起動・再読み込み・依存の追加（`uv sync`）が必要になるときは、事前に伝える。

### 秘密と安全
- **`.env` と `.env.example` は読まない・表示しない・変更しない。** API キーは利用者が `.env` に入れる。
- API キーはサーバ側だけで使う。サーバは 127.0.0.1 だけで待ち受ける。データはダミーだけを使う。

### Git・ドキュメント・テスト
- 確認なしにコミット・push しない（現在、このディレクトリは Git リポジトリではない）。
- README やドキュメントを頼まれずに作成・変更しない。ただし `docs/` 一式は利用者の依頼で作成したもので、上の方針で更新する。
- テストを確認なしに削除・コメントアウトしない。既存の動作するコードを理由なくリファクタリングしない。

### コードの書き方と検証
- 関数型寄りで、副作用を小さくする。
- 型を厳密にする（TypeScript で `any` を使わず `unknown` にする）。エラーは握りつぶさず、意味のあるメッセージを付ける。
- 複数行のコメントは、文字数ではなく意味の切れ目で改行する。
- 画面の挙動は Playwright（playwright MCP）で確かめる。スクリーンショットは `.playwright-mcp/` に置く。

## 3. 構成の概要

```
ブラウザ（React SPA）
  │  /api/*（同一オリジン）
  ▼
FastAPI（src/jevlab/web.py、127.0.0.1:8000）
  ├─ 評価ハーネス（/api/apps, /api/runs）── core/engine.py ── core/client.py ─┬─ Jev（api.typesafe.ai、課金）
  ├─ 運用（/api/ops）── ops/pipeline.py（ワーカー・シミュレータ）─────────────├─ Kev（127.0.0.1:8009、ローカル）
  │                      └─ ops/store.py（SQLite: var/ops.db）                  └─ MOCK（API を呼ばない）
  └─ ツール（/api/tools）── tools/tone.py ── core/generator.py ── claude -p（Claude Code、サブスク枠）
```

- **接続先（target）:** `jev` / `custom`（Kev などの互換サーバ）/ `mock` の 3 種類。1 つのサーバで同時に使い分ける。
  - Jev は `TYPESAFE_API_KEY` があるときだけ使える。
  - 既定の接続先は `JEVLAB_DEFAULT_TARGET` で決まる。
- **画面:** Vite 8 + React 19 + TypeScript（strict）+ react-router 8。
  - `frontend/` をビルドすると `src/jevlab/static/` に出力され、FastAPI が配信する。
  - 開発時は Vite（5173）が `/api` を FastAPI に中継する。
- **Python:** 3.12、uv で管理。依存は fastapi・typesafe-sdk・uvicorn だけ（開発用に pytest と ruff）。

### ファイルの地図

| パス | 役割 |
|---|---|
| `src/jevlab/web.py` | FastAPI 本体。起動時（lifespan）に接続先・Store・Pipeline・ワーカー・シミュレータ・書き換えの同時実行枠を用意し、評価 API と SPA の配信を持つ |

## 4. 主な設計判断と理由

詳細は `docs/adr/` にまとめる。要点は次のとおり。

| 判断 | 理由 |
|---|---|
| 1 つのサーバで Jev・Kev・MOCK を並べて使う（ヘッダーで切替・比較） | 同じデータで差を数字として見るため。閉域で Kev へ差し替える判断材料にする |
| 個人情報のガードは「規則で候補を拾う＋氏名だけモデルに聞く」 | 形で決まる種類（電話・メール・カード等）は規則のほうが確実で速い。形で決まらない氏名だけ Kev に「個人情報か」を聞く（Noul）。候補外に残っている可能性も 1 問で聞く |
| ガードの接続先は Kev か MOCK のみ（Jev は不可） | マスク前の本文を外部に出さないため |
| 個人情報の扱いはマスク／ブロック／検出のみの 3 択 | Amazon Bedrock Guardrails と同じ考え方。ブロックした件は人に回すか、Kev だけで仕分ける |
| 分類・項目抽出・優先度・担当の推定を 1 回の問い合わせにまとめる | Jev は 1 リクエスト内の質問を並列に判定し、質問を足しても増えるのは入力トークンだけだから |
| 項目抽出は「候補を選ばせる」方式 | Jev は文章を生成しない。規則で拾った候補を Choice のキーにし、「該当なし」を加えて選ばせる |
| 振り分けは確信度のしきい値で決める（既定: 自動 ≥0.9、確認待ち ≥0.5、それ未満はエスカレーション） | 強い不満・緊急は業務ルールで常にエスカレーション。しきい値は「閾値の調整」画面で目標の誤り率から逆算して提案する |
| 学習ループはモデルの再学習ではなく「しきい値の調整」と「例を読ませる」 | Jev には fine-tuning がない。人の確認結果を正解にしきい値を見直し、担当の推定では最近の完了例を判定のたびに渡す |
| 担当は、推定の確信度が高いとき（既定 ≥0.7）だけ自動で割り当てる | 残りは推定を表示して人が決める。推定の当たり具合は、人が決めた件だけで測る（自動のままの件は必ず一致するため） |
| 外に出る見出し（投稿・担当の例）は、個人情報の候補をすべて伏せる | 伏せすぎは読みにくいだけだが、漏れは取り返せない |
| まとめて処理では、編集していない件の候補をすべてマスクする。人が編集した件は、その下書きで処理する | 本文を見ていない件は安全側に倒し、人の判断があればそれを尊重する |
| 言い方チェックは「判定＝Jev/Kev、生成＝Claude」 | Jev は判定だけを返す。書き換えは判定結果を入力に Claude が作り、それを Jev で判定し直して比べる |
| 書き換えは `claude -p`（サブスク枠）で、Generator の抽象の裏に置く | すぐに試せ、あとで Anthropic API 版に差し替えられる。既定は sonnet（6 文面 × 3 モデルの比較で速さと質の釣り合いが最良） |
| 運用データは SQLite 1 ファイル（`var/ops.db`） | デモ・検証用途で十分。読み出し・変更・保存をロックの中で行い、ワーカーと画面操作の競合を防ぐ |

## 5. 起動・テスト・検証

### 起動（利用者が行う）
```
scripts/dev.sh --kev     # 開発用: FastAPI(8000, 自動再起動) + Vite(5173)。画面は http://127.0.0.1:5173
scripts/start.sh --kev   # ビルドしてから起動。画面は http://127.0.0.1:8000
scripts/serve.sh --mock  # ビルド済みを起動（--mock は API を呼ばない、引数なしは既定 Jev で .env が必要）
```
- 利用する環境変数（値は `.env` に入れる。`.env` は読まないこと）:
  - `TYPESAFE_API_KEY`
  - `KEV_URL`（既定 http://127.0.0.1:8009）
  - `KEV_TIMEOUT_S`
  - `JEVLAB_DEFAULT_TARGET`
  - `JEVLAB_BUDGET_USD`
  - `JEVLAB_VAR_DIR`
  - `JEVLAB_GENERATOR`
  - `JEVLAB_CLAUDE_USE_API_KEY`

### テスト用サーバ（Claude が検証に使う）
- 利用者のサーバとぶつからないよう、別ポートと別のデータ置き場で起動する。
  ```
  env -u TYPESAFE_API_KEY -u TYPESAFE_BASE_URL JEVLAB_DEFAULT_TARGET=mock \
    JEVLAB_VAR_DIR=<作業用ディレクトリ>/var8010 KEV_URL=http://127.0.0.1:8009 \
    nohup uv run uvicorn jevlab.web:app --host 127.0.0.1 --port 8010 > <作業用ディレクトリ>/srv8010.log 2>&1 &
  ```
- 止めるときは `pkill -f "[u]vicorn jevlab.web:app --host 127.0.0.1 --port 8010"` を**単独のコマンドとして**実行する（後述の落とし穴を参照）。
- デモデータを流すには、`POST /api/ops/simulator` に `{"playing": true, "interval_s": 0.5}` を送る。

### テストと静的チェック
```
uv run pytest -q
uv run ruff check src tests && uv run ruff format --check src tests
cd frontend && npx tsc -b && npm run lint && npm run build
```
- テストは MOCK で動く（`tests/conftest.py` の `mock_env` が環境変数を差し替え、Kev には接続しない）。

### 画面の検証
- Playwright（playwright MCP）でテスト用サーバを操作して確かめる。
- Playwright のサンドボックスでは `URL` や `Buffer` が使えないので、正規表現やファイルのパスで代用する。

## 6. 現状（2026-09-26）

### できていること
- **評価ダッシュボード:** 8 アプリのライブ評価（単独・比較）、単発判定、評価履歴。
- **運用ダッシュボード**（手順は [walkthrough.md](walkthrough.md) を参照）
  - 受付箱、個人情報の確認（まとめて処理・下書き保持）、分類の確認（キー操作・絞り込み・抜き取り）
  - エスカレーション（担当の推定・自動割り当て・まとめて割り当て・対応目安）、チャンネル（疑似 Slack）
  - 担当者（一覧の編集・当たり具合）、コネクタ（疑似の Gmail/Slack/API、CSV 取り込み）
  - 閾値の調整、設定、ダッシュボード（流れ図・KPI・受信シミュレータ・経過）
- **ツール:** 言い方チェック（判定・目的の上書き・文ごとの見え方・Claude の書き換え案・書き換え後の再判定と比較）。
- **テスト:** pytest 133 件すべて成功。型チェック・lint・build にエラーなし。

### 実測の記録
- **Kev の個人情報検出（デモ 60 件）:** 検出 43・見落とし 3・誤検出 0。
  - 見落とした 3 件も「判断のつかない候補」として人の確認に回ったので、人の確認を経ずに Jev に届いた件はない。
- **Kev の速さ:** 言い方チェック 1 回（17 問）で約 10 秒。CPU 実行のため、個人情報の確認の処理が詰まりやすい（ボトルネック）。
- **Jev の利用額:** デモ 64 件を流して約 $0.0017。自動処理率は 60%、自動振り分けの正解率は 18/18。
- **書き換えのモデル比較（Kev で判定し直して測定）**

  | モデル | 時間の中央値 | 指摘の数 前→後 |
  |---|---|---|
  | sonnet | 7.2 秒 | 38→27 |
  | opus | 8.5 秒 | 38→22 |
  | haiku | 32.3 秒 | 38→24 |

  既定は sonnet。Kev の再判定は結果がぶれるので、数字は目安。

### 残っている小さな課題
- 「氏名の可能性」という表示名の見直し。実際は「未確定の候補がある」という意味で、氏名に限らない。
- サーバの入力チェックのエラー（422）が、画面に JSON のまま出ることがある。

## 8. 既知の落とし穴（このプロジェクトで実際に踏んだもの）

| 落とし穴 | 対処 |
|---|---|
| `pkill -f uvicorn...` を、同じ文字列を含むシェルコマンドの中で実行すると、そのシェル自身が止まる（終了コード 144） | `pkill -f "[u]vicorn ..."` のように角括弧で自分自身に一致しない形にし、起動スクリプトとは別のコマンドで実行する |
| `scripts/dev.sh` で Vite（5173）が起動直後に止まり（状態 `T`）、画面が開かない | `set -m` で別のプロセスグループにした裏の Vite が端末の入力を読み、SIGTTIN で停止していた。Vite の入力を `/dev/null` にして解決。停止時は `kill -CONT` で再開させてから終了させる |
| pydantic のモデルに `target` という名前の項目を作ると、同名のモジュール `target` を型注釈で参照できなくなる（`'str' object has no attribute 'Target'`） | `from jevlab.core.target import Target` のように型を直接 import する |
| Kev で質問数が多い判定（言い方チェックの 17 問）が 10 秒でタイムアウトした | Kev クライアントの待ち時間を 120 秒に延ばした（`KEV_TIMEOUT_S`） |
| `asyncio.Semaphore` をモジュールの読み込み時に作ると、最初に使ったイベントループに結び付き、別のループ（別の TestClient）で落ちる | 起動時（lifespan）に `app.state` に作る |
| `claude -p` に親プロセスの環境変数が渡り、`ANTHROPIC_API_KEY` があると従量課金で動く | 子プロセスには `TYPESAFE_*`・`KEV_*`・`ANTHROPIC_API_KEY` を渡さない。API 課金に切り替えるときだけ `JEVLAB_CLAUDE_USE_API_KEY=1` にする |
| Score（段階評価）の値は段階の期待値。「くだけすぎ」と「堅すぎ」に割れると真ん中（適切）に見える | 真ん中が良い軸は「適切」の段階の確率で判定する |
| MOCK の確信度が一定だと、何も自動で振り分けられない | MOCK は文面から決まる疑似乱数で確信度を散らしている |
| ダークモード用の CSS の一括指定で、Slack 風のサイドバーの文字が暗くなった | 除外クラス（`.ch-btn` など）を足す |
| 文面の JSON を Playwright の中で扱うとき、`URL`・`Buffer` がない | 正規表現やファイルのパスで代用する |
| 待機に `sleep` を前面で使うとブロックされる環境がある | バックグラウンド実行や、条件を満たすまで待つループを使う |
| CJK（日本語）の判定精度は英語より低い（TypeSafe の注意事項） | 質問文は短く、1 問 1 条件にし、候補を選ばせる形にする |
