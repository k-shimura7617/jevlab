## 1. 目的と経緯

- **目的:** TypeSafe の **Jev**（System One モデル）を少額（$5）で試し、用途別の小アプリで何に使えるかを見極める。閉域向けに、SDK 互換の **Kev**（ローカル・CPU）へ差し替える構成も試す。
- **経緯（2026-09-25〜27）:** 評価ダッシュボード（8 アプリ）→ 運用ダッシュボード（個人情報ガード → 分類 → 振り分け／人の確認、実際の Slack、ファイル取り込み、分類の編集）→ ツール（言い方・返信前・契約・規約チェック）の順に作った。
- 詳しい流れは `git log` と [adr/](adr/README.md) を正とする。
- 動作確認に使うマシンは GPU なし・RAM 30GB・16 コア。Kev（0.8B 相当）を CPU で動かすため、個人情報の確認が詰まりやすい。
- リポジトリの置き場所は `~/develop/2026/jevlab`（2026-09-26 に `jev` から改名済み。8 章を参照）。

## 2. 利用者の方針（CLAUDE.md にないもの）

### やりとり
- 常に敬語。簡潔に。冗長を嫌う。1 項目 1〜2 行。締めの要約や、聞かれていない指摘は付けない。
- 利用者の案を否定する前に、まず意図を確認する。
- 確信がないことは「確認できていない」と書く。訂正するときは訂正だけする。
- 許可を求めるときは前提（何が起きるか・なぜ要るか）を書く。確認の回数は減らす。
- 設定作業（Slack など）は、こちらから手順を 1 つずつ出して先導する。
- 並行作業の結果は、全部終わってから大見出しの一覧だけ出し、選ばれたものを 1 つずつ詳しく出す。
- 工数は AI 駆動の工数で見積もる。
- 「企業に見せられる」は、デモ用の仕掛けではなく「実務でそのまま通用する流れ」のこと。

### 名前
- 決まっている名前の例: 「AI返信案」「AI返信案の作成」「採用」「方針」「判定する」「返信内容の検討」「この内容で返信」「処理フロー」「対応待ち」「完了済みの問い合わせとして取り込む」「個人情報チェック」「自動の完了を取り消す」。
- ボタン名にカッコ書きを付けない（例: 「判定する（Ctrl+Enter）」は不可）。

### 画面
- 押しやすい大きさ・読みやすい余白にする。長い説明は画面に並べず「？」（`Hint`）に入れる。
- 設定は自動保存。選択系は変えたら保存、確認は危険な操作（ガードを外す・「検出のみ」・担当者の削除）だけ。
- 重大な操作（全削除など）は「本当に〜しますか？」で確認し、終わったらポップアップで知らせる。
- 生成中に離れる・別の操作をするときは「生成を中止しますか？」で確認する。
- 折りたたみは、開いた中身の下にも「閉じる」を置く（`components/fold.tsx`）。
- 件の詳細は受付箱で開く。メールで返信（`mailto:`）は新しいタブで開く。

### 業務の考え方
- 使う人は CS 担当とリーダー（非エンジニア）。何も考えずに使えることを優先し、細かい調整は開発側が請け負う（[ADR-0030](adr/0030-user-screens-and-admin.md)）。
- 設定の項目を増やさない。対応目安（SLA）と優先度の重みによる並び替えは要らない（外した）。
- 成績は「見て、ボタン 1 つで合わせる」形にする。数値の手入力はさせない。
- 返信の要る分類（問い合わせ・クレーム・その他）は、担当を割り当てて（届かなければ仮で）メンションし、人が完了にする。
- お礼（返信不要）は確認不要。投稿し、スレッドに「対応不要のため完了にしました。」を書いて ✅ を付け、完了にする。メンションはしない。
- 「その他」は件ごとに Jev で「返信が要るか」（`needs_reply`）を判定する。
- 返信不要の分類は、確信度が自動の閾値以上なら、不満・緊急の兆しがあっても完了にする。返信の要否を判定する分類では、強い不満・緊急の兆しがあれば自動で完了にしない（順番は [ADR-0029](adr/0029-route-order-table.md)）。誤って自動で完了にした件は「自動の完了を取り消す」で戻せる。
- Slack のリンクは、エスカレーションの投稿ならエスカレーションの画面、それ以外は受付箱で開く。
- 確認中の件の返信に、返品・交換の期限や手順を書かない。書いてよい期日は、こちらから連絡する時期だけ。
- 見本のデータは、ID だけ変えた量産にしない。内容をばらばらに作る。
- ファイル取り込みの「完了済み」は既定オフ（目的は閾値の試算。Jev の精度は上がらない）。

## 5. 起動・テスト・検証

### 起動（利用者が行う）
```
scripts/dev.sh --kev     # 開発用: FastAPI(8000, 自動再起動) + Vite(5173)
scripts/start.sh --kev   # ビルドしてから起動（8000）
scripts/serve.sh --mock  # ビルド済みを起動（引数なしは既定 Jev で .env が必要）
```
- Kev は別リポジトリで動かす（jevlab の中では動かない）。
  ```
  (cd ~/develop/2026/kev && env -u VIRTUAL_ENV uv run --extra serve python -m kev.serve --run jaredpalmer/kev-0.8b --port 8009)
  ```
- 環境変数の一覧は [architecture.md](architecture.md) の「設定と環境変数」。値は `.env` に入れる（`.env` は読まない）。

### テスト用サーバ（Claude が検証に使う）
```
env -u TYPESAFE_API_KEY -u TYPESAFE_BASE_URL JEVLAB_DEFAULT_TARGET=mock \
  JEVLAB_VAR_DIR=<作業用ディレクトリ>/var8010 KEV_URL=http://127.0.0.1:9 \
  nohup uv run uvicorn jevlab.web:app --host 127.0.0.1 --port 8010 > <作業用ディレクトリ>/srv8010.log 2>&1 &
```
- `KEV_URL=http://127.0.0.1:9` で Kev に届かない状態にする（利用者の Kev を使わない）。Kev で確かめるときだけ 8009 にする。
- 止めるときは `pkill -f "[u]vicorn jevlab.web:app --host 127.0.0.1 --port 8010"` を単独のコマンドとして実行する。
- デモデータを流すには `POST /api/ops/simulator` に `{"playing": true, "interval_s": 0.5}`。

### テストと静的チェック
```
uv run pytest -q
uv run ruff check src tests && uv run ruff format --check src tests
cd frontend && npx tsc -b && npm run lint && npm run build
```
- 全件通る。テストは MOCK で動き、Kev には接続しない（`tests/conftest.py`）。
- 画面をビルドしていない環境（新しい clone・worktree）では、`tests/test_web.py` の 1 件が 503 で落ちる。先に `npm ci && npm run build`。

### 画面の検証
- Playwright（playwright MCP）でテスト用サーバを操作する。スクリーンショットは `.playwright-mcp/` に置く。
- Claude の生成（AI返信案・説明など）は押さない（利用者が試す）。`claude -p` の確認は最低限にする。

## 8. 既知の落とし穴

| 落とし穴 | 対処 |
|---|---|
| `pkill -f uvicorn...` を、同じ文字列を含むシェルの中で実行すると、そのシェル自身が止まる | `pkill -f "[u]vicorn ..."` と書き、単独のコマンドで実行する |
| `scripts/dev.sh` で Vite（5173）が起動直後に止まる（状態 `T`） | Vite の入力を `/dev/null` にして解決済み。止まったら Ctrl+Shift+R か dev.sh の再起動 |
| Kev を jevlab のフォルダで起動すると「Extra `serve` is not defined」 | `~/develop/2026/kev` で起動する（5 章） |
| ディレクトリ名の変更（`jev` → `jevlab`、済み） | `.venv` は絶対パスを持つので `rm -rf .venv && uv sync`。Claude Code のメモリはパスごと（`~/.claude/projects/-home-...-jevlab/memory/`）なのでコピーした。`git worktree prune` も行った |
| アカウントを切り替えると、claude.ai のコネクタ（Gmail・Calendar・Drive）と engineering プラグインの MCP が外れる | ローカルの MCP（playwright・context7・brave-search・drawio・filesystem）は使える。`claude -p` は新しいログインで動く。`gh` の認証は別。以前の Artifact は前のアカウントに残る |
| 別アカウントの組織で Claude Code のサブスク利用が無効だと、サブエージェントが 403（`oauth_org_not_allowed`）で止まる | アカウントを切り替え、止まった worktree の作業を引き取って続ける |
| pydantic の項目名 `target` が同名のモジュールを隠す | `from jevlab.core.target import Target` と型を直接 import する |
| Kev で質問数が多い判定がタイムアウトした | 待ち時間 120 秒（`KEV_TIMEOUT_S`） |
| `asyncio.Semaphore` をモジュール読み込み時に作ると、別のイベントループで落ちる | 起動時（lifespan）に `app.state` に作る |
| `claude -p` に `ANTHROPIC_API_KEY` が渡ると従量課金で動く | 子プロセスに渡さない。API 課金にするときだけ `JEVLAB_CLAUDE_USE_API_KEY=1` |
| Score の値は期待値。両端に割れると真ん中に見える | 真ん中が良い軸は「適切」の段階の確率で判定する |
| ダークモードの一括指定で、Slack 風のサイドバーや日付欄の色が崩れた | 除外クラスと `color-scheme: dark` で直した |
| Playwright のサンドボックスに `URL`・`Buffer` がない | 正規表現やファイルのパスで代用する |
| 前面の `sleep` がブロックされる環境がある | バックグラウンド実行や、条件を満たすまで待つループを使う |
| CJK（日本語）の判定精度は英語より低い | 質問は短く 1 問 1 条件にし、候補を選ばせる |
| クラウドのセッションは利用者の PC と別環境で、8000・5173・8009 に届かない。push が 403 になることもある | 画面や Slack の設定は利用者の手元で。push は GitHub の接続し直しを利用者に頼む |
| 変数の設定とバックグラウンド起動を 1 行にすると、変数が後のコマンドで空になる | 変数は別の文で設定し、起動は `( ... & )` で包む |
| Playwright の `setInputFiles` に日本語のファイル名を渡すと、変更イベントが起きないことがある | ASCII の名前に写してから渡す |
| Prettier の設定がない | Prettier は使わない。周りの書き方に手で合わせる |
| Slack の `channel_join` などは消せない（`cant_delete_message`） | 全削除は、このアプリが投稿したものだけを対象にし、消せない投稿は飛ばす |
| Slack の転送・経過の書き足しは、つないだ後の分だけ流す | テストでは先に `tick()` してから件を作る |
| 自動の worktree の中で、`git` という語を含む文字列を python に渡すと実行を止められることがある | ファイルの編集は Edit ツールで行う |

## 9. 再開するときの最初の手順

1. `CLAUDE.md`、このファイル（特に 2 章・7 章・8 章）、[walkthrough.md](walkthrough.md) を読む。
2. PR のセルフマージの許可が続いているかを利用者に確かめる。
3. 利用者のサーバを読み取りだけで確かめる（`curl -s 127.0.0.1:8000/api/ops/overview`・`curl -s 127.0.0.1:8009/v1/models`）。
4. `git pull origin main` してから、テストを流して現状を確かめる。
5. 修正はブランチ（worktree）で行い、区切りで完結したレポートを出して `docs/` を更新する。
