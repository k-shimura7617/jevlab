# Jev / TypeSafe の知見

> 一次情報はリポジトリ直下の `SKILL.md`（TypeSafe 公式のスキル定義）と、公式ドキュメント（<https://docs.typesafe.ai/llms.txt> から辿る）です。
> 以下はこのプロジェクトで実際に使い、確かめた内容です。
> 数値（料金・上限・モデル名）は 2026-09 時点のものなので、使う前に公式ドキュメントで確認してください。
> 紹介動画から得た追加の知見は [research/](research/) にまとめます。

## 1. System One という考え方

- **Jev の性格**
  - TypeSafe の Jev は、文章を生成するモデルではありません。自然言語とアプリの状態を読み、**型の決まった判定と確率**を返します。
  - 理由の説明や推論の過程は返しません。
  - 人の「速い直感的な判断」（System One）にあたる部分をプログラムの部品として使う、という位置づけです。
- **役割分担**
  - **ワークフローはコードが持ちます。** 規則・計算・完全一致の照合・実行はコードで書きます。
  - モデルは、コードでは書けない「意味の分かる常識」だけを受け持ちます。
- **このプロジェクトでの分担:** Jev は「判定」を受け持ち、「文章の生成」は Claude が受け持ちます（[ADR-0001](adr/0001-jev-for-judgment-claude-for-generation.md)）。

## 2. 3 つの型（プリミティブ）

| 型 | 答えの意味 | 返るもの | 使いどころ |
| --- | --- | --- | --- |
| **Choice** | 決められた選択肢のうち 1 つ | 選んだキー、確信度、選択肢ごとの確率 | 分類、担当者の選択、候補の中から値を選ぶ |
| **Score** | 順序のある段階の上での位置 | 確率で重み付けした位置（期待値）、確信度、段階ごとの確率 | 不満度、返金要求の強さ、丁寧さ |
| **Noul** | 条件が成り立つか | 「はい」の確率（確信度は別に無い） | 緊急か、個人情報か、皮肉か |

注意点（実際に踏んだものを含む）:

- **Noul の 0.5 は「強さが中くらい」ではありません。** 「はい」と「いいえ」が同じくらいありうる、という意味です。
- **Score の値は期待値です。**
  - 段階の確率で重み付けした位置なので、両端に割れると真ん中の値になります。
  - 例: 「くだけすぎ 0.5 / 堅すぎ 0.5」の値は 1.0 で、真ん中の「適切」に見えてしまいます。
  - 真ん中が良い軸では、真ん中の段階の確率そのものを見ます（言い方チェックの丁寧さで修正済み）。
- **Choice / Score の確信度が表すもの:** 分布の集中度です。ワークフロー全体の正しさや、「実行してよい」という許可ではありません。害のない好みの選択なら、低い確信度でも問題ないことがあります。
- **確率が 0.5 付近のときの読み方:** 型が保証するのは答えの形であって、中身が正しいことではありません。閾値は、自分のデータと、誤ったときの重さで決めます。

## 3. 問い合わせの組み立て

1 回の問い合わせは **state（状態）＋ questions（質問の集まり）** です。各質問は **instructions（何を判定するか）** と **criteria（答えの定義）** を持ちます。

```python
await client.system_one(
    state={"mail": {"body": text}},                   # 判定に必要な事実。名前付きの JSON にする
    questions={
        "category": Choice(
            instructions="`mail.body` を内容に応じて 1 つに仕分ける",  # state はバッククォートのパスで参照
            criteria={"inquiry": "...", "complaint": "...", "thanks": "...", "other": "..."},
        ),
        "urgent": Noul(instructions="`mail.body` に、すぐ対応しないと実害が出る状況が書かれている"),
    },
)
```

- **質問の ID はモデルに送られません。** 意味は instructions と criteria に書き切ります。
- **独立した質問はまとめて 1 回で聞きます。** 並列に判定され、往復は 1 回です。質問を足しても、増えるのはトークン代だけです。ただし、質問どうしは互いの答えを見られません。
- **後から前の答えが要る場合だけ、2 回目の問い合わせを出します。** 前の答えで次の選択肢や根拠を作る場合です。
- **推測で聞く質問（speculative）も使えます。** たとえば担当者の推定は、エスカレーションになるかどうかが分かる前に一緒に聞いておき、エスカレーションになったときだけ使います。

## 4. 料金・上限・性能

| 項目 | 値（2026-09） |
| --- | --- |
| 料金 | 入力 $0.042 / 100 万トークン。出力は無料 |
| モデル | jev-1.13.0（別名 jev-latest / jev-preview） |
| 文脈の長さ | 64k トークン |
| Choice の選択肢 | 最大 255（このプロジェクトでは「どれでもない」の分を残して 254 まで） |
| Score の段階 | 最大 10 |
| 1 回あたりの固定分 | 約 280 トークン（実測） |
| 言語 | 日本語などの CJK は英語より精度が下がるとされる。自分のデータで確かめる |

実測の目安（このプロジェクト）:

| 判定の内容 | 時間 | 料金 |
| --- | --- | --- |
| メール 1 件の仕分け（分類＋優先度＋項目抽出＋担当推定） | Jev で 1 秒前後 | 約 $0.0001 以下 |
| 言い方チェックの 17 問 | Kev（CPU）で約 10 秒 | 無料 |

## 5. Kev（互換サーバ）

- Kev は Jev と同じ API で答える、手元（CPU）で動くサーバです（既定 `http://127.0.0.1:8009`）。
- SDK の `base_url` を向けるだけで切り替えられます。課金はありません。
- 用途:
  - 閉域の想定
  - 元の本文を外に出せない判定（個人情報）
  - Jev との比較
- 注意点:
  - CPU 実行のため遅く、SDK の既定タイムアウト（10 秒）では足りないことがあります。このプロジェクトでは 120 秒にしています（`KEV_TIMEOUT_S`）。
  - 同時に 1 本しか流さないようにしています。
  - 精度は Jev と同じではありません。実測では、氏名の確率が本物でも 0.2〜0.9 とばらつきました。そのため個人情報の候補の閾値を低め（0.3）にし、迷う件は人に回しています。

## 6. このプロジェクトで使ったパターン

| パターン | どこで | 要点 |
| --- | --- | --- |
| **選ばせる抽出**（select instead of generate） | 注文番号・期限・金額の抽出 | 候補はコード（正規表現）が拾い、候補の文字列そのものを Choice のキーにして「どれでもない」を足す。モデルは値を作らないので、候補にない値は出てこない（[ADR-0005](adr/0005-candidate-selection-extraction.md)） |
| **多観点のスコアと並べ替え**（composite scoring） | 優先度 | 不満度・緊急・返金・公にする可能性を 1 回で判定し、重み付けはコードと画面で行う。重みを変えても判定し直さない（[ADR-0006](adr/0006-priority-in-code.md)） |
| **確認とエスカレーション**（verify and escalate） | 振り分け | 確信度の閾値で「自動 / 人の確認 / 人の判断」に分ける。業務ルール（強い不満・緊急）は確信度より優先（[ADR-0007](adr/0007-human-in-the-loop-queues.md)） |
| **閾値の調整**（学習ではなく） | 閾値の調整画面 | 人が確認した結果を正解として、閾値ごとの自動処理率と誤り率の曲線を描き、目標の誤り率を満たす閾値を提案する（[ADR-0004](adr/0004-threshold-tuning-not-finetuning.md)） |
| **Kev 前段**（安いモデルで確定できるものは確定） | 分類（設定で有効化） | Kev の確信度が十分なら Jev を呼ばない |
| **候補ごとの判定**（ガード） | 個人情報 | 規則で拾った候補ごとに Noul。「候補以外が残っているか」の Noul を足して取りこぼしを補う（[ADR-0002](adr/0002-kev-pii-guardrail.md)） |
| **説明と例つきの Choice** | 担当者の推定 | 選択肢の説明に、担当範囲と最近の対応例（人が割り当てて完了した件の見出し）を入れる。学習せずに、判定のたびに例を読ませて精度を上げる（[ADR-0008](adr/0008-assignee-auto-assign-threshold.md)） |
| **目的に応じて観点を切り替える** | 言い方チェック | 目的（依頼・謝罪・お礼…）を Choice で判定し、目的に合う観点だけで総合判定する。観点はすべて 1 回で聞いておき、使う・使わないはコードで決める |

## 7. 良い質問（criteria）の書き方

1. **1 つの質問では、1 つのまとまった判定だけを聞きます。** 独立して役に立つ観点は分けます。ただし、判定する関係そのものを壊すほど細かくはしません。
2. **state には、答えるのに必要な事実を名前付きで置きます。** 質問からは `` `mail.body` `` のように、バッククォートのパスで参照します。
3. **criteria は具体的な状況で書きます。**
   - Score の各段階は、それだけ読んで意味が分かる文にします。
   - Noul は「〜である」という状態を述べる文にして、`true` と `false` の意味を両方書くと安定します。
4. **当てはまらない場合の答えを用意します。**
   - Choice には「どれでもない」を入れます。
   - 選ばせる抽出では、候補の取りこぼしを確かめます。候補にない値は、モデルには選べません。
5. **方針はコードに置きます。**
   - 「重大な違反が 1 つでもあれば止める」のようなルールは、重み付きの合計にせず、個別の条件で判定します。
   - 生の判定は再利用できる形で残します。
6. **失敗の原因を分けて調べます。** 分けるのは、根拠の不足・モデルの誤り・コードの誤り・サービスの障害の 4 つです。state・質問・候補・答え・組み立て・結果を、それぞれそのまま確かめます。

## 8. 閾値の考え方（このプロジェクトの既定）

| 閾値 | 既定 | 意味 |
| --- | --- | --- |
| 自動の閾値 | 0.9 | これ以上なら自動で振り分ける |
| 確認の閾値 | 0.5 | これ以上なら人の確認。未満ならエスカレーション |
| 候補の閾値 | 0.3 | 氏名の候補を個人情報と確定する。見逃しの方が重いので低め |
| 残りの閾値 | 0.5 | これ以上なら「見落としの可能性」として人に見せる |
| 担当の自動割り当て | 0.7 | これ以上なら自動で割り当てる |
| 言い方チェック | 悪い方の確率 0.6 以上で「要見直し」、0.4 以上で「気になる」 | |

これらは出発点です。閾値の調整画面で、実データの結果から見直します。
