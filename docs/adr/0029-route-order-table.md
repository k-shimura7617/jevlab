# 0029. 仕分けの順番を 1 つの表にまとめ、行ごとにテストで固定する

- 状態: 採用
- 日付: 2026-09-27
- 関連: [ADR-0007](0007-human-in-the-loop-queues.md)、[ADR-0017](0017-confidence-semantics.md)、[ADR-0027](0027-editable-categories.md)

## 背景と課題

- 自動完了・エスカレーション・判断の割れ・担当の仮割り当てを、別々の時期に足してきた。
  どれが先に効くかがコードのあちこちに散り、組み合わせでぶつかった。
  - 例: お礼の件で、自動の完了より先に別の条件が効き、担当に仮で割り当ててメンションすることがあった。
- テストは部品ごとで、「受信から Slack まで」の流れを通して確かめるものがなかった。
  - 例: 受付箱を空にすると、Slack に何も流れなくなった。

## 決定

- 仕分けの順番を、`src/jevlab/ops/pipeline.py` の表（コメント）1 か所で決める。
  - 最初の振り分けは `decide_route`、自動で振り分けた後は `after_route` が表のとおりに動く。
- 表の行ごとに `tests/test_ops_route_order.py` で 1 件ずつ固定する。行を足す・順番を変えるときは、表・この ADR・テストを一緒に直す。
- 使う流れに沿ったテストを `tests/test_ops_flows.py` に置く。受信 → ガード → 仕分け → 振り分け → Slack（偽物）を通しで流す。Jev の答えだけを台本にする。

### 最初の振り分け（上から順に見て、最初に当てはまったもので決める）

| 行 | 条件 | 結果 |
|---|---|---|
| R1 | 返信のいらない分類で、分類の確信度 ≥ 自動の閾値 | 自動（不満・緊急の兆しや担当の推定では止めない） |
| R2 | 強い不満（P(不満度 2) ≥ 設定値） | エスカレーション（設定でオフにできる） |
| R3 | 緊急 | エスカレーション（設定でオフにできる） |
| R4 | 確信度 ≥ 自動の閾値で、判断が割れている | 確認待ち |
| R5 | 確信度 ≥ 自動の閾値で、判断材料が足りない | 確認待ち（設定でオフにできる） |
| R6 | 確信度 ≥ 自動の閾値 | 自動 |
| R7 | 確信度 ≥ 確認の閾値 | 確認待ち |
| R8 | それ以外 | エスカレーション |

### 自動で振り分けた後

| 行 | 条件 | 結果 |
|---|---|---|
| A2 | 返信が要らない | 完了（Slack には投稿し、スレッドに「対応不要のため完了にしました。」と ✅） |
| A3 | 返信が要る | 担当を割り当てる（確率が閾値に届かなければ仮で） |

返信が要らないのは、返信のいらない分類の件と、返信の要否を判定する分類で強い不満・緊急の兆しがなく P(返信が要る) < 0.5 の件。

## 結果

- 良い点: どの条件が先に効くかを表 1 つで答えられる。順番を変えると、どの行が変わったかをテストが示す。
- 悪い点: 表とコードは手で合わせる。テストが行ごとにあるので、ずれればテストで気づく。
