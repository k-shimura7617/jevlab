# 0003. 保存は SQLite、処理は同じプロセスの非同期ワーカーで行う

- 状態: 採用
- 日付: 2026-09-26
- 関連: [architecture.md §2.4](../architecture.md#24-運用受付箱--srcjevlabops)

## 背景と課題

受付箱は、受信・判定・人の操作が並行して起きる。
検証用のアプリなので、運用の手間は小さくしたい。一方で、再起動しても状態が残り、処理が途中で止まっても回復できる必要がある。

## 検討した選択肢

1. メモリだけに持つ
2. PostgreSQL と、別プロセスのジョブキュー（Celery など）
3. **SQLite（1 ファイル）と、FastAPI と同じプロセスの非同期ワーカー**

## 決定

選択肢 3 を採用する。

- **保存:** `var/ops.db` に items / events / posts / settings の 4 表を持つ。件の中身は JSON で持つ。
  - スキーマを変えなくても、項目を足せる（pydantic の既定値で古いデータも読める）。
- **排他:** 接続は 1 本で、ロックで守る。
  - 「読み出し・変更・保存」を 1 トランザクションで行う（`Store.update`）。
  - ワーカーと画面の操作の書き込みが重ならないようにするため。
- **ワーカー:** 同時 3 件まで処理する。接続先ごとに同時数を絞る（Kev 1、Jev 4）。
  - 1 件の失敗は件に記録して、全体を止めない。
- **起動・停止時の回復**
  - 起動時: 「処理中」のまま残った件を「処理待ち」に戻す。
  - 停止時: 処理中のタスクを取り消す。
- **番号:** 受付箱を空にしても、番号は戻さない。空にする前の処理の結果が、新しい件に書き込まれないようにするため。

## 結果

- 良い点
  - 依存が増えず、1 コマンドで起動できる。
  - 再起動しても状態が残る。
- 悪い点
  - 複数のサーバで同じ受付箱を分担することはできない（本番化するなら PostgreSQL とキューに分ける）。
  - 検索・集計は、件を読み出してから Python で行う。件数が増えたら見直す。
