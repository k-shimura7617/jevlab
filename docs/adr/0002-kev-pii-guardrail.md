# 0002. 個人情報のガードは Kev で行い、形で決まるものは規則で確定する

- 状態: 採用
- 日付: 2026-09-26
- 関連: [architecture.md §7](../architecture.md#7-安全の境界)、[0010](0010-server-side-pii-draft.md)

## 背景と課題

問い合わせの本文には、氏名・電話・住所・カード番号などの個人情報が含まれる。

- 仕分けには外部の Jev を使うが、元の本文を外部に送りたくない。
- ただし、個人情報かどうかを判定するには、元の本文を読む必要がある。

## 判断の基準

- 元の本文を外部に送らない
- 見逃し（送ってしまう）を、誤検出（余計に伏せる）より重く扱う
- 閉域でも動くこと

## 検討した選択肢

1. 規則（正規表現）だけで検出してマスクする
2. Jev に元の本文を送って判定させる
3. **規則で候補を拾い、形で決まらない候補だけをローカルの Kev に判定させる。迷う件は人が確認する**

## 決定

選択肢 3 を採用する。

- **規則で確定する種類:** 電話・メール・郵便番号・住所・カード・口座・生年月日。形で決まるので、規則だけで確定する。
- **Kev に聞くもの:** 氏名の候補と、「候補以外に個人情報が残っていないか」の 2 つだけ。Kev はローカルなので、元の本文を渡してよい。
- **判定の接続先:** 型（`GuardTarget`）で Kev / モックに限る。Jev は選べない。
- **しきい値:** 見逃しの方が重いので、候補を確定するしきい値は低め（0.3）にする。
- **人の確認:** 個人情報が見つかった件と、迷う件は人の確認に回す（設定で切り替えられる）。
- **方針:** 種類ごとに「検出のみ」「マスク」「ブロック」を選ぶ（Bedrock Guardrails の考え方にならう）。ブロックした件は Jev に送らない。
- **サーバ側の安全策:** 規則で確定した構造的な個人情報は、画面から外されてもサーバ側で戻す（送られてきた内容をそのまま信じない）。

## 結果

- 良い点
  - Jev に届くのはマスク済みの本文だけになる。
  - デモデータ 60 件で、規則の検出は 46/46 件、誤検出は 0 件だった（このデータに合わせて調整したもの）。
  - Kev の実測では、取りこぼした 3 件もすべて人の確認に回った。
- 悪い点
  - Kev は CPU で動くため遅く、処理のボトルネックになる。対策として「Kev を使わない」モードを検討中（handoff.md のやることリスト）。
  - 規則はデータに合わせて調整したものなので、実データでは見直しが必要。
