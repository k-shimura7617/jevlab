# 0013. 実際の Slack とのつなぎ込みは Socket Mode と同期 SDK で行う

- 状態: 採用
- 日付: 2026-09-26
- 関連: [slack-setup.md](../slack-setup.md)（設定の手順）、[ADR-0007](0007-human-in-the-loop-queues.md)、[ADR-0008](0008-assignee-auto-assign-threshold.md)

## 背景

- 運用デモの疑似チャンネル（#cs-… など）に加えて、実際の Slack ワークスペースへの投稿と、Slack からの受信を試したい。
- jevlab は 127.0.0.1 でだけ待ち受ける。そのため、Slack の Events API（Slack から HTTP で呼び出す方式）に必要な公開 URL がない。
- 投稿してよいのは、個人情報を伏せた見出しだけ（ガードレールの方針）。

## 決定

1. **受信は Socket Mode で行う。** アプリから Slack に WebSocket でつなぐので、公開 URL もトンネルもいらない。
2. **SDK は `slack-sdk` の同期版を使う。**
   - 送信（`chat.postMessage`）は `asyncio.to_thread` に逃がす。
   - 受信は SDK のスレッドから `loop.call_soon_threadsafe` でイベントループに戻し、既存の `Pipeline.ingest` に渡す。
   - 非同期版は aiohttp などの追加の依存が要るため使わない。
3. **送信は「投稿の転送」として作る。** 疑似チャンネルへの投稿（posts テーブル）を 2 秒ごとに見て、新しい投稿のうち Slack のチャンネル ID を割り当てたものだけを送る。仕分けの処理は Slack を知らないままにする。
   - 起動時と無効の間は「いまの最新」から数える。過去分はまとめて送らない。
   - 一時的な失敗（429 など）は、待ち時間を伸ばしながら同じ投稿から送り直す。
   - 設定の誤り（`not_in_channel` など）は、その投稿を飛ばしてエラーを表示する。
   - お問い合わせ窓口（元の本文）は、割り当てがあっても送らない。
4. **受信は新しい受信経路 `slack` として取り込む。** 疑似チャットの `chat` とは分ける。
   - コネクタの接続・切断を別々にできる。
   - 受付箱で経路を見分けられる。
   - 既定は切断で、既存の設定にも影響しない。
5. **トークンは環境変数から読む。** `SLACK_BOT_TOKEN`・`SLACK_APP_TOKEN` を `uv run --env-file .env` で渡し、画面や API には出さない。どちらかがなければ、その方向は「未設定」として何もしない。
6. 設定（転送の有無・チャンネルの割り当て・受信するチャンネル）は運用の設定（SQLite）に置き、コネクタ画面から変える。受信の接続・切断は、次の周期で反映する。
7. **エスカレーションは「親の投稿＋スレッドの返信」に分ける。**
   - 親の投稿には画面へのリンクを付け、その `ts` を件に残す（`slack_channel`・`slack_ts`）。
   - 担当の割り当て・変更・完了は、同じスレッドへの返信で知らせる。担当者に Slack ID があればメンションする。
   - 担当が未定の件は、振り分け担当（当番）を呼び出す。対応目安（営業時間）の N 分前になっても未定なら、1 件につき 1 回だけ知らせる。
   - 親の投稿の応答が返らなかったときは、送り直す前に Slack 側にリンクの印を含む投稿があるかを確かめ、二重に投稿しない。
8. **受信の重複は、メッセージのキーで防ぐ。** 取り込んだメッセージのキーを `seen_messages` 表に残し、再接続で同じメッセージが届いても 1 回だけ取り込む。

## 結果

- 良い点
  - 公開 URL なしで双方向につながる。
  - 仕分けの処理は変えずに済む。
  - 失敗しても仕分けは止まらない。
- 注意点
  - 依存に `slack-sdk` が増える。取り込みには `uv sync` と、サーバの起動し直しが要る。
  - 転送は最大 2 秒遅れる。
  - Slack のユーザー名は取らない（`users:read` を求めない）。差出人はユーザー ID で表示する。
  - スレッドの返信は取り込まない。元の件への追記として扱う仕組みは今後の課題。

## 検討した他の案

- **Events API ＋ トンネル（ngrok など）:** 外部に口を開けることになり、閉域の想定に合わない。
- **非同期 SDK（AsyncWebClient・aiohttp）:** 依存が増える。量が少ないので、スレッドに逃がす方式で十分。
- **パイプラインの投稿箇所で直接送る:** 送信の失敗や待ちが仕分けに影響する。投稿の箇所が複数あり、漏れやすい。
