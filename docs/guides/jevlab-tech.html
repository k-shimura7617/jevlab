jevlab 技術ガイド

判定は Jev、文章は Claude、個人情報は手元の Kev

jevlab は、型の決まった答えと確率を返す AI（Jev）で問い合わせを判定し、その確率をもとにコードが「自動で流す／人に回す」を決めるアプリです。
元の本文は外に出さず、手元のサーバ（Kev）と規則で個人情報を伏せてから送ります。

Jev と Kev とは

Jev

決めた形で答える AI（外部・有料）

TypeSafe 社が提供する判定専用の AI です。
文章を作らず、「どれか 1 つ」「何段階のどこか」「はい・いいえ」の形で答え、その確率を返します。
コードは確率を見て、自動で進めるか人に回すかを決めます。

Kev

手元で動く Jev 互換のモデル（無料）

小さなオープンの LLM（Qwen）を、Jev と同じ使い方ができる判定専用のモデルに作り替えたものです。
API が Jev と同じなので、接続先を変えるだけで入れ替えられます。
第三者が作ったもので、TypeSafe の公式のものではありません。

MOCK

AI を呼ばない試験用

本物と同じ形の答えを作って返します。
料金をかけずに画面と流れを確かめるときに使います。

接続先どこで動くか料金精度の目安このアプリでの役目
JevTypeSafe のサーバ（外部）使った分だけ（1 件 約 $0.00004）正解率 約 0.86問い合わせの分類・担当の推定、ツールの判定。伏せた本文だけを送る
Kev手元の PC（いまは CPU）なし0.8B で 0.65〜0.70、4B〜27B で 0.82〜0.90個人情報の判定（元の本文を外に出さないため）、Jev との比べ、閉域で使う想定の確かめ
MOCKアプリの中なし当てにならない（試験用）画面と流れの確認、試験

正解率は、Kev の公開資料にある「学習に使っていない種類のデータ」での値です。
自分たちのデータでは変わるので、成績の画面で確かめます。

構成

元の本文（手元だけ）伏せた本文・見出し（外へ出る）アプリの中の流れ

問い合わせ 1 件の流れ

  1. 受信：メール・チャット・Slack・ファイル・API のどれから来ても、同じ流れに乗せます。
  2. 個人情報ガード：電話・メール・カードなど形で決まるものは規則で確定し、氏名の候補だけを Kev に聞きます。候補があれば人の確認で止めます。
  3. 仕分け：伏せた本文を Jev に送り、分類・不満度・緊急・項目の抽出・担当の推定を 1 回の問い合わせでまとめて判定します。
  4. 振り分け：確信度と業務ルールを、決まった順番（順番表）で当てはめ、「自動で振り分け／分類の確認／エスカレーション」を決めます。
  5. その後：返信の要るものは担当を割り当てて Slack でメンションし、要らないものは完了にして ✅ を付けます。
  6. 見直し：人が確かめた結果を正解にして成績を出し、自動にする基準のおすすめを出します。

Jev（TypeSafe System One）

TypeSafe 社が提供する、判定専用の AI です（外部のサービス・有料）。
文章を作るのではなく、決めた形の答えと確率を返します。
人の「速い直感的な判断」（System One）にあたる部分を、プログラムの部品として使います。

仕組み

  • アプリの状態（state）と質問の集まり（questions）を送ると、質問ごとに型どおりの答えと確率が返る
  • 理由の説明や推論の過程は返さない
  • ワークフロー（規則・計算・実行）はコードが持ち、Jev は「コードでは書けない常識の判定」だけを受け持つ

このアプリでは

  • 問い合わせの分類・不満度・緊急・項目の抽出・担当の推定
  • ツールの判定（言い方・返信前・契約）
モデル
jev-1.13.0（2026-09）
料金
入力 $0.042 ／ 100 万トークン、出力は無料
1 回の固定分
約 280 トークン（実測）

Kev（互換サーバ）

小さなオープンの LLM（Qwen）を、Jev と同じ使い方ができる判定専用のモデルに作り替えたものです。
Jev の仕組みを推定した公開記事をもとに第三者が作ったオープンソースで、TypeSafe の公式のものではありません。
接続先を向け替えるだけで切り替えられ、料金はかかりません。

仕組み

  • SDK の接続先（base_url）を 127.0.0.1:8009 に向けるだけで、同じ質問がそのまま動く
  • CPU で動くため遅い（1 回に数秒〜10 秒）。待ち時間は 120 秒にしている
  • 同時に 1 本だけ流す

このアプリでは

  • 個人情報の判定（元の本文を読むので、外部の Jev には任せない）
  • 閉域で使う想定の確かめと、Jev との比べ
  • 「Kev で先に判定」：Kev の確信度が十分なら Jev を呼ばない（管理画面で有効化）

アーキテクチャ

  • 土台は Qwen3.5 の Base モデル（0.8B／4B／9B。27B は Qwen3.8）。土台の重みは固定したまま
  • 学習するのは、rank 16 の LoRA アダプタと、小さな pointer head の 2 つだけ
  • 状態と質問を 1 つの列にし、各選択肢の </opt> と質問の最後の <decide> の位置の内部表現を pointer head で照らし合わせて点数にし、softmax で確率にする
  • Choice・Score・Noul のどれも「選択肢の点数付け」として同じ仕組みで答える。質問どうしは互いを見ない
  • モデルごとに 1 つの温度で確率をならす（0.8B は 2.35）。1 位の答えは変わらない
  • 学習データは公開データ約 1 万件と、生成した規則の例。Jev の出力は使っていない

なぜ手元で動くのか

  • 小さい：0.8B なら fp32 でも重みは約 3GB で、普通の PC のメモリに載る
  • 文章を生成しない：1 回の順伝播で出た点数から答えるので、1 文字ずつ作る処理が要らない
  • 公開された重み（アダプタと pointer head）を土台に載せるだけで動く
いま動いているもの
jaredpalmer/kev-0.8b、CPU・torch・fp32
速さの目安
言い方チェック 17 問で約 10 秒（この PC）。同じ 0.8B でも Apple M5 なら 5 問 約 0.15 秒、L4 GPU なら 6 問 約 0.02 秒（公開資料の値）
正解率
0.8B 0.65〜0.70、4B・9B 約 0.82〜0.85、27B 0.85〜0.90、Jev 0.857（学習に使っていない種類のデータ）
注意

いま使っている 0.8B は、精度が Jev より低めです。
氏名の確率が 0.2〜0.9 とばらつくため、候補の基準を低め（0.3）にし、迷う件は人に回しています。
精度を上げるなら、4B を GPU で動かすか、自分たちのデータで追加学習（LoRA）させます。

MOCK

AI を呼ばずに、それらしい答えを返す試験用の接続先です。
料金をかけずに画面と流れを確かめるのに使います。

  • 確信度は、本物と同じ式で確率から計算する
  • 自動・確認・エスカレーションがすべて起きるように、答えをばらつかせる
  • 同じ本文には同じ答えを返す（試験の結果が安定する）

3 つの型

Jev に聞く質問は、答えの形で 3 つに分かれます。

型答え返るものこのアプリの例
Choice選択肢から 1 つ選んだもの・確信度・選択肢ごとの確率分類、担当者、注文番号の候補
Score順序のある段階の上の位置期待値・確信度・段階ごとの確率不満度、返金の強さ、丁寧さ
Noul条件が成り立つか「はい」の確率緊急か、個人情報か、返信が要るか
読み方のこつ

Noul の 0.5 は「中くらい」ではなく「どちらもありうる」です。
Score の値は期待値なので、両端に割れると真ん中に見えます。段階ごとの確率を見て判断します。

確信度

確信度は「最大の確率」そのものではなく、答えの分布がどれだけ集中しているかを表します。
このアプリの自動・人の振り分けは、この値で決めます。

Choice

確信度 = (pmax − 1/N) ÷ (1 − 1/N)　　N = 選択肢の数

当て推量（1/N）からどれだけ伸びたかです。
選択肢の数が変わると、同じ確率でも値が変わります。

Score

確信度 = max(0, 1 − D ÷ B)　　D = 最大の段階からの距離の期待値、B = 段階の中央からの平均距離

離れた段階に確率があるほど下がり、両端に割れると 0 になります。

このアプリでの工夫

担当者の推定は、人数で選択肢の数が変わるため、確信度ではなく「推定した人の確率」で自動の割り当てを決めます（0.7 以上）。

1 回の問い合わせ（state ＋ questions）

判定に必要な事実（state）と、質問の集まり（questions）を 1 回で送ります。
独立した質問は並べて聞けば、往復は 1 回で済みます。

  • 質問は「何を判定するか（instructions）」と「答えの定義（criteria）」で書く。質問の ID はモデルに送られない
  • 質問を足しても、増えるのはトークンの料金だけ。ただし質問どうしは互いの答えを見られない
  • 前の答えが要るときだけ、2 回目を出す
  • 担当の推定は、エスカレーションになるか分かる前に一緒に聞いておき、必要なときだけ使う
このアプリでは

問い合わせ 1 件につき、分類・不満度・緊急・返金・公にする恐れ・情報不足・返信の要否・注文番号などの抽出・担当の推定を、1 回でまとめて聞いています。

選ばせる抽出

注文番号・期限・金額は、AI に作らせずに、コードが拾った候補から選ばせます。

  • 正規表現で候補を拾い、候補の文字列そのものを Choice の選択肢にする
  • 「どれでもない」を足して、当てはまらない場合を選べるようにする
  • 候補にない値は出てこないので、ありもしない番号を作ることがない

個人情報ガード

外部の AI に送る前に、手元で個人情報を見つけて伏せます。
見逃しの方が重いので、迷うものは人に見せます。

仕組み

  • 形で決まる種類は規則で確定：電話・メール・郵便番号・住所・カード・口座・生年月日・SNS アカウント
  • 氏名の候補ごとに Kev に Noul で聞く（0.3 以上で個人情報）
  • 「候補のほかに残っていないか」も Noul で聞き、0.5 以上なら人に見せる
  • 方針はマスク／ブロック／検出のみ。カード・口座は既定でブロック（送らない）

守っていること

  • 規則で確定した箇所は、画面から外されてもサーバで戻す
  • 送った後に見逃しに気づいたら、件の詳細から報告できる（改善の記録）
  • Kev を使わない設定では、候補をすべて伏せる（安全側）

仕分けの順番表

自動・確認・エスカレーションは、決まった順番で上から当てはめ、最初に当たったもので決めます。
順番は 1 か所で決め、行ごとにテストで固定しています。

行条件結果
R1返信の要らない分類で、確信度 ≥ 自動の基準自動（そのまま完了）
R2強い不満（不満度 2 の確率 ≥ 0.35）エスカレーション
R3緊急エスカレーション
R4確信度 ≥ 自動の基準で、判断が割れている確認待ち
R5確信度 ≥ 自動の基準で、判断の材料が足りない確認待ち
R6確信度 ≥ 自動の基準（既定 0.9、分類ごとに変えられる）自動
R7確信度 ≥ 確認の基準（既定 0.5）確認待ち
R8それ以外エスカレーション

自動で振り分けた後は、返信が要るかで分けます。
要るものは担当を割り当て、要らないもの（お礼、宣伝など）は完了にします。

担当の推定

担当者を選択肢にした Choice で、誰の担当かを推定します。
学習はせず、判定のたびに説明と例を読ませます。

  • 選択肢の説明に、担当範囲の文と、最近その人が対応した例（伏せた見出し）を入れる
  • 例に使うのは、人が割り当てて完了した件だけ（AI の推定をそのまま例にしない）
  • 推定した人の確率が 0.7 以上なら自動で割り当て、届かなければ一番確率の高い人に仮で割り当てる
  • 担当範囲の案は、完了した例から Claude に書かせられる

成績と基準の提案

モデルを学習し直すのではなく、自動にする基準（確信度の閾値）を見直します。

  • 正解は、人が確かめた件（分類の確認で決めた・分類を見て完了にした件）
  • 基準を 0.50〜0.99 で動かしたときの「自動にする割合」と「誤りの割合」の曲線を描く
  • 誤りが 5% 以下になる、いちばん低い基準をおすすめする（正解が 20 件未満なら出さない）
  • 分類の混同行列で、どの分類を取り違えやすいかを見る
  • 分類の定義（説明）を変えたら、変えた後の件だけで数える

Slack 連携

Socket Mode でつなぐので、外から届く公開の URL は要りません。
アプリが正本で、Slack は知らせる場所です。

  • 振り分けた件を分類のチャンネルに投稿し、担当をメンションする。担当の変更・完了はスレッドに書き、完了で ✅ を付ける
  • 送信は送った位置を記録し、応答が返らなかった投稿は Slack 側を探して二重に送らない
  • 受信したメッセージは受付箱に取り込み、同じ流れ（ガード → 仕分け）に乗せる
  • 投稿の全削除は、このアプリが投稿したものだけを消す

文章の生成（Claude）

判定は Jev、文章を書くのは Claude と役割を分けています。

  • 書き換え案・AI返信案・契約の説明・担当範囲の案を、claude -p（Claude Code の CLI）で作る
  • モデルは sonnet（既定）と opus
  • AI返信案は書いた分から順に表示（ストリーミング）し、途中で止められる
  • 子のプロセスには API キーや Jev・Kev の設定を渡さない

安全の境界

  • 運用の問い合わせは、伏せる前の本文を外部（Jev・Claude・Slack）に送らない
  • 外に出る見出し（Slack の投稿・担当推定の例）は、個人情報の候補をすべて伏せる
  • サーバは 127.0.0.1 だけで待ち受ける
  • 生成の子プロセスに秘密（API キーなど）を渡さない
  • Jev の利用額に上限を設ける（既定 $1.00）
  • 監査ログは本文や電話番号を含めずに書き出す
