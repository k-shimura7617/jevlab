## (c) 修正 — 動画から見て、今の使い方が最適でない点

### C1. 強い不満の判定を P(2) で行う（工数 S・優先度 高）
- 根拠: Score の確信度の説明（41:00〜45:00）。確率 0.55/0.05/0.40 のように両端に割れると、期待値は 0.85 で「1（不満）」に丸められるが、実は 40% の確率で「強い不満」。
  スライドでは、この形の確信度は 0 になっている。
- 現状: `src/jevlab/ops/pipeline.py` の `decide_route` は `frustration.prediction == 2`（期待値を四捨五入した段階）で、強い不満のエスカレーションを決めている。
  割れた件は、強い不満の可能性が高くても自動で振り分けられうる。
- 提案:
  - `answers["frustration"].probabilities["2"] >= しきい値（例 0.35）` でエスカレーションにする。
  - Score の確信度が低い（割れている）ときは「分類の確認」に回す。
  - しきい値は設定画面と閾値の調整画面で変えられるようにする。
- 同じ扱いにしたい所: 優先度の `refund`（Score）も期待値で並べているが、並び順の用途なので影響は小さい。

### C2. 確信度の閾値は選択肢の数に依存する（工数 S・優先度 高）
- 根拠: Choice の確信度 `(p_max − 1/N) / (1 − 1/N)`（38:30〜41:00）。
- 影響:
  - 分類（N=4）の自動の閾値 0.90 は p_max ≈ 0.925、確認の閾値 0.50 は p_max = 0.625 に当たる。N が固定なら問題はない。
  - **担当者の推定**（`src/jevlab/ops/questions.py` の `assignee_question`、N = 担当者の数 + 1）は、担当者を増減するたびに同じ閾値 0.70（`AssignSettings.threshold`）の意味が変わる。4 人なら p_max 0.76、10 人なら 0.727。
  - 言い方チェックの目的（N=6）・印象（N=4）の確信度も、選択肢を足すと下がる。
- 提案:
  - 担当推定は `probabilities` の最大値（p_max）で自動割り当てを判定する。設定画面の文言も「推定の確率」にする。
  - 分類の閾値は今のままでよいが、カテゴリを追加・削除したら閾値を見直すように、閾値の調整画面で注意を出す。

### C3. MOCK の確信度を公式の式で出す（工数 S・優先度 中）
- 根拠: 同上。
- 現状: `src/jevlab/core/client.py` のモックは、Choice の確信度に最大確率そのもの（0.45〜0.99）を返し、Score の確信度は 0.6 に固定している。
  本物の Jev とは、同じ分布でも値がずれる。
- 提案: モックの確率分布から、Choice は `(p_max − 1/N)/(1 − 1/N)`、Score は `max(0, 1 − D/B)` で確信度を計算する。
  閾値の調整の練習（MOCK）で見える自動処理率が、本物に近づく。

### C4. 言い方チェックの丁寧さ（確認のみ・工数なし）
- 根拠: 「独自の確信度が欲しければ確率から計算せよ」（44:00〜）。
- 今の実装（`src/jevlab/tools/tone.py` の `_politeness`。「適切」の確率 P(1) で判定し、向きは P(0) と P(2) で決める）は、公式の考え方に沿っている。変更は不要。

## (a) 既存アプリの改善

### A1. 判断が割れている件を人に回す（工数 S・優先度 高）
- 根拠: 確率が低い（割れた）問題は正解率も低い傾向（10:40〜11:20）。Score の確信度は、割れると 0 になる（43:00）。
- 提案（`decide_route`）:
  - 分類の Choice で、上位 2 つの確率の差が小さい（例 < 0.2）なら、確信度にかかわらず「分類の確認」に回す。
  - 緊急（Noul）や不満（Score）が 0.4〜0.6 付近にあるときも同様に扱う。
  - 閾値の調整画面に「割れている件」の数を出す。

### A2. Noul の「成立」寄りの偏りを測る（工数 M・優先度 中）
- 根拠: 「過剰に OK と見なす場合が多い」「誤検知も目立つ」（10:10〜10:25、23:50）。
- 影響する所:
  - 個人情報の候補判定と残存の Noul（`src/jevlab/ops/questions.py` の `guard_questions`）
  - 言い方チェックの観点（`src/jevlab/tools/tone.py` の `ASPECTS`、しきい値 `BAD_AT` 0.6 / `WARN_AT` 0.4）
  - 評価ダッシュボードの各アプリ
- 提案:
  - 評価ダッシュボードの結果から、質問ごとに「真の否に対する平均 P(yes)」を出して偏りを見える化する。
  - 質問ごとにしきい値を持てるようにする。
  - 良い方が yes になる観点（例:「期限・日時が明確」）は、偏りがあると問題を見逃す向きに働く。「期限が書かれていない」のように、問題を yes にする文面に揃えることも検討する。
  - 肯定形と否定形の質問で確率が整合しない（65:10）ので、1 つの観点は 1 つの向きの問いに固定する（同じ観点を肯定・否定の両方で聞いて平均する、のような使い方はしない）。
  - 同じ入力でも実行ごとに確率が揺らぐ（64:30）ので、評価ダッシュボードで同じデータを 3 回流し、閾値付近でどれだけ判定が入れ替わるかも測る。

### A3. 確信度の意味を画面で説明する（工数 S・優先度 中）
- 根拠: スライドの応答例で「確率 0.85 なのに確信度 0.78」（16:30〜18:00）。
- 提案:
  - 閾値の調整画面・評価ダッシュボード・運用の件の詳細に、確信度の式と「最大確率とは違う」ことを短く出す（ツールチップ）。
  - 件の詳細では、確信度と最大確率を並べて表示する。

### A4. 会話は State を発言の配列で渡す（工数 S・優先度 中）
- 根拠: State は文字列・JSON・配列を受け付ける（29:00 付近、19:00 の質疑）。
- 提案: 実際の Slack とのつなぎ込みでスレッドを取り込むときは、`["発言1", "発言2", …]` の配列で State に入れる。
  長いメールの引用部分も、段落の配列にすると、どの部分を根拠にしたかを文ごとの質問で聞きやすい。
- 関係する所: `src/jevlab/ops/questions.py` の `classify_state`。

### A5. Score に「判断できるか」のゲートを付ける（工数 S・優先度 中）
- 根拠: Score に「不明」の段階は入れられないので、Noul「判断できる情報が書かれているか」を同じリクエストに並べ、その確率で Score を使うかを決める（35:30〜36:40）。
  質問を並べても State の計算は使い回される。
- 対象:
  - 運用の不満度・返金要求（`src/jevlab/apps/mail/questions.py` の `frustration`、`src/jevlab/ops/questions.py` の `refund`）
  - 言い方チェックの丁寧さ（相手・場面の情報が薄い文面）
- 例: 「返金についての言及がある」が低ければ、返金度 0 と見なして優先度に入れない（今は期待値のまま足している）。

### A6. criteria と State の書き方を版で比べる（工数 M・優先度 中）
- 根拠: criteria を詳しく書く、State に事例を入れるなどは試行錯誤の余地が大きく、入力が安いので文章量の増加は問題にならない（34:00〜34:40）。
  State を組み立てる関数を差し替え可能にしておくのがよい（34:40）。
- 現状: jevlab は State を組み立てる関数（`classify_state` など）を分けてあるので、差し替えの土台はある。
- 提案: やれることリストの「定義（criteria）の版管理と旧版／新版の比較」を先に進める。
  評価ダッシュボードで同じデータに版 A・B を流し、正解率・偏り（A2）・確信度の分布を並べる。
  担当者の推定では、例を criteria の説明に入れる今の方式と、State に入れる方式を比べる。

## (b) 新しいアプリ・機能の案

### B1. 返信テンプレのリランキング（工数 M・優先度 中）
- 根拠: リランキングのユースケース（61:30〜62:30）。
- 内容:
  1. エスカレーションの件ごとに、社内の返信テンプレ（数十件）を Noul「このテンプレはこの問い合わせへの返信の土台になる」で採点し、上位 3 件を出す。
  2. 選んだテンプレと件の本文（マスク済み）を Claude に渡して下書きを作る。
- 言い方チェックの「書き換え案」と同じ構成（Jev で選ぶ → Claude で作る → Jev で判定し直す）で、対応時間を縮められる。
- やれることリストの ① にあたる。

### B2. 日本語の推論力を測る評価セット（工数 M・優先度 中）
- 根拠: 発表者の日本語 NLI の結果（09:00〜10:10）。知識の問題は 77%、ほかは 82〜86%。
- 内容: 前提文と仮説文の組（帰結・矛盾・中立）を数十件、評価ダッシュボードの新しいアプリとして追加し、Jev と Kev の正解率と偏りを並べる。
  日本語の業務文面で、どこまで Jev を信じてよいかの根拠になる。

### B3. 社内依頼のルーター（工数 M・優先度 低）
- 根拠: ツールのルーティングと Skills の選定（57:30〜61:00）。
- 内容: 社内の依頼文を、申請先・ツールの一覧から Choice で選び、確率の上位 X 件を出す。
  そのうえで Noul「作業（アクション）を求めているか」「単なる質問か」をゲートにして、フォームに回すか、FAQ で返すかを分ける。
- やれることリストの ⑤ にあたる。

### B4. 文書とコードの整合チェック（工数 L・優先度 低）
- 根拠: 発表者の使い道の構想（07:50〜08:40）。
- 内容: ADR や設計書の各決定事項と、関連するコードの抜粋を組にし、Noul「このコードはこの決定に従っている」で矛盾の候補を拾う。
  このリポジトリの `docs/` と `src/` で試せる。
- 注意: 「過剰に OK と判定しがち」（A2）なので、見逃しの率を先に測る必要がある。
